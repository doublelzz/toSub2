# run哥 CDK 邮箱验证排查与修复

排查日期：2026-11-24，Asia/Shanghai。

## 结论

根因是 Codex OAuth 补充邮箱验证的分支没有实现。程序完成密码和 2FA 登录后，`/api/accounts/session/select` 返回 `email_otp_send`，旧程序把它当成授权暂时不可用，输出 `CODEX_EMAIL_VERIFICATION_REQUIRED` 后正常退出。控制台随后把任务标记成 `login_ready`，显示“已登录”，因此既没有发送这一步的邮件，也没有启动自动取码或提供手动验证码输入。

邮箱链接已配置并不保证程序会进入取码分支；原来的自动轮询只在子进程输出 `Email OTP (r=resend, q=quit):` 时启动。上述提前退出发生在这个提示之前。

## 远程证据

- 服务为 ARM64 容器 `tosub2`，镜像 `tosub2:f68d7a085814-arm64`，远程源码 revision 为 `f68d7a0`。
- 已定位备注为“run哥”的 CDK；另有“run哥老板”，后者未发现任务文件。
- “run哥”的任务目录中有 60 条带 `CODEX_EMAIL_VERIFICATION_REQUIRED` 的历史元数据，其中 4 条带邮箱链接。该数字是磁盘记录统计，不代表当时运行中的任务数量。
- 样本 `8511041c-3968-4575-bb03-07638a2295fb` 重试日志明确记录“已记录收码接口中的 0 个旧邮件验证码标识”，随后恢复已有网页登录，调用 `session/select` 后再次输出上述 pending 标记并结束。说明重试时链接已被读取，但补充验证分支没有继续执行。
- 样本 `9aca22b3-270d-415f-936d-29be0f990dc4` 同样在密码、2FA、网页登录会话保存之后停止在该分支。
- 两条样本邮箱链接实测均返回 HTTP 200、JSON，字段为 `email`、`code`、`mail`；本次读取时均未提取到验证码。此结果不能单独判断邮件投递速度，但结合任务日志可以确认原流程没有触发补充验证的发码和轮询。

检查通过 SSH、只读文件/数据库查询以及应用查询接口完成。临时查询会话已退出；未提交验证码、购买号码、重试真实账号或重启远程服务。

## 修复方式（已在本地实现）

1. `protocol-login.mjs` 识别 `email_otp_send`、`email_otp_verification` 和邮箱验证页面，继续完成补充验证。需要发码时按返回地址执行 GET 导航，保留当前登录会话和代理；已经发码的验证页直接等待验证码。
2. 进入现有的邮箱验证码输入流程：配置链接的账号复用自动轮询；无链接的账号保留手动输入、错误码重填和重新发码。验证通过后根据服务端返回结果继续手机号绑定、工作区选择或 OAuth 回调。
3. 记录本次发码开始时间，复用既有的新邮件过滤和已用验证码标识，避免直接提交先前网页登录用过的验证码。
4. 控制台解析新邮箱验证阶段的提示时，排除先前密码和 2FA 阶段的提示。局部回归已复现旧的 2FA 日志会覆盖 `email_otp` 状态并中断轮询，此处一并修正。
5. 历史上被误标成“已登录”的受影响任务恢复为 `resume_available`，提示“待邮箱验证”，提供“继续流程”入口。保留已保存的网页登录会话、2FA 和换绑能力，不自动批量重启历史账号任务。

## 2026-11-25：无邮箱链接时延后补充验证

未发起接码且没有邮箱链接的账号，在 Codex 要求补充邮箱验证时先停为“待接码”，保留网页登录及登录检查点，不进入这一步的手动验证码输入。点击单个或批量“开始接码”后，重新使用已有会话检查 Codex 返回；仍需邮箱验证才发送邮件并显示手动输入，不再需要验证则直接继续授权。有邮箱链接的账号继续自动取码。

首次网页登录自身需要的邮箱验证码不受此规则影响。历史待验证任务在尚未发起接码、没有邮箱链接时恢复为“待接码”，并保留账号管理入口。

本地 `test/codex-email-gate-console.mjs` 已覆盖：无链接延后验证、单个开始接码后手动填写、批量开始接码时挑战已解除、密码＋2FA 登录无提前手动邮箱提示、有链接继续自动验证、历史恢复及重新尝试。协议与控制台回归继续通过。
